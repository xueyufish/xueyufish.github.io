## 写在前面

最近读了《深入理解 AI Agent》这本书，作者是李博杰（bojieli），全书围绕一个公式展开：**Agent = LLM + 上下文 + 工具**。第一章是概念地图，快速建立了理解 Agent 系统的基本框架。这篇笔记是对第一章的梳理，夹杂一些我自己的理解。

---
## Part 1：Agent 是什么
### 核心公式：Agent = LLM + 上下文 + 工具

这三者分别对应：

- **LLM 是大脑**：理解意图、思考规划、做出判断。能力来自预训练（世界知识）和后训练（决策策略）
- **上下文是眼睛**：Agent 在每个决策点能看到的全部信息——环境、记忆、知识、状态
- **工具是手脚**：Agent 能做的所有事情——从 API 调用到代码执行，从委托子 Agent 到主动与用户沟通

用更学术的说法，这三者对应强化学习中的策略（Policy）、观察空间（Observation Space）和动作空间（Action Space）。

### 五类工具

Agent 的工具按互动方向分为五类：

- **感知工具**：获取信息（搜索、文件系统、API）
- **执行工具**：改变世界（代码执行、文件操作、外部 API 调用）
- **协作工具**：与其他 Agent 或人类协作（委托子 Agent、请求确认）
- **事件触发工具**：外部输入驱动 Agent 执行（新邮件、定时器、Webhook）
- **用户沟通工具**：主动向用户传递信息（消息、语音、邮件）

### 工具调用的四步循环

1. 告诉模型有哪些工具可用
2. 模型判断要不要调用、调哪个、传什么参数
3. 工具执行，结果追加到上下文
4. 模型据此决定下一步

这个循环就是 **ReAct**（Reasoning + Acting）的基础——思考→行动→观察→思考→行动→观察，不断重复直到任务完成。

> **引用**：ReAct 论文来自 Yao et al., 2023，[arXiv:2210.03629](https://arxiv.org/abs/2210.03629)

## Part 2：LLM 的能力边界

### 内部思考

LLM Agent 的一个独特能力是**内部思考**——在采取实际行动之前，先进行规划与推演。这一过程不改变外部环境，却能显著提升后续行动的质量。

这种能力来自预训练阶段习得的逻辑规则——数学定律、因果关系、问题分解策略。所以 Agent 的推演不是盲目探索，而是在结构化的知识体系上展开。

### 零样本泛化与少样本适应

- **零样本泛化**：即使面对从未见过的任务，也能通过组合已有知识来处理
- **少样本适应**：只需两三个示范例子，就能掌握新的任务模式

### 模型即 Agent：新范式

"模型即 Agent"代表了最新方向。先进模型通过后训练将工具调用能力内化为原生能力：何时调用、调哪个、传什么参数，都由模型自己决定。

但这不意味着框架层变得不重要。恰恰相反，模型越强大，围绕模型构建的 **Harness** 就越关键。Harness 原指马具，不是为了限制马的奔跑能力，而是把这种力量引导到正确的方向上。

### 《苦涩的教训》与 Harness 的关系

Rich Sutton 在 2019 年的《苦涩的教训》（[原文链接](http://www.incompletenessideas.net/IncIdeas/BitterLesson.html)）中回顾了 AI 研究七十年间反复上演的一幕：研究者一次次把对领域的理解编码进系统，短期见效，长期却总是输给能随算力与数据规模持续扩展的通用方法。

本书的立场是八个字：**方向认同，节奏务实**。方向上，模型会持续吃掉 Harness；但节奏上，这个"吃"远比直觉慢——模型此刻的能力边界，就是 Harness 此刻的价值所在。

这就像自动驾驶。L2 辅助驾驶（Harness）和 L4 完全自动驾驶（模型原生能力）不是二选一，而是一个渐进的过程。在 L4 还没到来之前，L2 就是刚需。

### Agent 的三种学习机制

| 学习范式 | 机制 | 比喻 |
|---------|------|------|
| **后训练** | 强化学习将经验固化到模型参数 | 学教科书——永久提升，成本高 |
| **上下文学习** | 注意力机制在上下文中模式匹配 | 查参考资料——临时有效，用完就忘 |
| **外部化学习** | 知识和流程外部化为知识库和工具 | 整笔记本——持久保存，随时可查 |

**关键区分**：上下文学习的内部机制更接近**模式匹配而非真正的学习**。它能让模型套用已见过的模式，但不能发现全新的规律。

打个比方：给你看三道相同类型的数学题和答案，然后给你第四道，你大概率能照葫芦画瓢做出来——这就是上下文学习。但如果第四道题需要一种全新的解题思路，光看前三道题的答案是不够的。

## Part 3：上下文的五个组成部分

上下文是 Agent 在每个决策点能看到的全部信息。从 API 视角看，每次调用 LLM 时的上下文由五部分构成：

**静态前缀**（整个对话过程中保持不变）：
- **系统提示词**：定义 Agent 的身份、权限和行为准则
- **工具定义**：声明可用工具的名称、功能描述和参数格式

**动态历史**（随交互不断增长）：
- **用户消息**：来自用户的输入，可能包含通过 RAG 检索的外部知识
- **模型回复**：包含思考过程、文本内容和工具调用请求
- **工具执行结果**：Agent 框架执行工具后返回的结果

## Part 4：消融实验——上下文为什么重要

### 实验设计

通过**消融实验**（逐一去掉某个组件，观察整体性能变化），验证每个上下文组件是否不可或缺。系统提示词不参与消融——没有它，Agent 连基本角色认知都没有。

### 实验结果

- **去掉工具定义**：Agent 完全丧失行动能力，无法识别和调用任何工具
- **去掉工具执行结果**：Agent 陷入无限循环，反复调用同一个工具
- **去掉思考过程**：前后决策互相矛盾，缺少之前决策的原因
- **去掉历史消息**：重复执行已完成的步骤，等于失忆

**核心洞察**：上下文决定了 Agent 能看到什么，而 Agent 只能基于它看到的信息做决策。

**我的体会**：这解释了为什么很多 Agent 产品"看起来聪明，用起来蠢"——不是模型不行，而是上下文设计有问题。Agent 看不到该看的信息，自然做不出正确的判断。

## Part 5：Harness 工程——从 Demo 到生产

### 从能跑 Demo 到可靠产品的鸿沟

前面的实验证明了基本机制有效，但也暴露了脆弱点：模型可能产生幻觉、选错工具、遇到错误时无法自我恢复。一个能跑的 Demo 和一个可靠的产品之间有巨大鸿沟。

### Agent = Model + Harness

用方程展开生产形态下的完整组成：

> **Agent = LLM + [上下文 + 工具 + 约束 + 验证 + 纠正] = Model + Harness**

Harness 五个功能分为两层：

**能力层**（让 Agent 能做事）：
- **上下文**：为模型提供感知信息
- **工具**：为模型提供行动手段

**保障层**（让 Agent 不做错事）：
- **约束**：设定行为边界——能做什么、不能做什么
- **验证**：自动判断操作结果的对错
- **纠正**：发现问题时自动修正或回退

### 举例理解

假设你让 Agent 帮用户退掉 3 天前的订单：

**没有 Harness 时**：模型看不到退款政策（缺上下文），不知道该调哪个 API（缺工具），直接编造退款结果（缺验证），用户发现退款没发生（缺纠正）。

**有了 Harness 后**：系统提示词写明 7 天退款政策（上下文），Agent 调用查询和退款工具（工具），框架校验退款金额不超过订单金额（约束），校验数据库状态确认退款成功（验证），API 超时则自动重试（纠正）。

同一个模型，有无 Harness，结果天壤之别。

### 行业转变

**行业正在从"能做事"向"可靠地做事"转变，Harness 工程成为 Agent 系统的核心竞争力。**

以 Claude Code 为例，它的 Harness 中绝大部分代码都是约束、验证与纠正，而非上下文与工具。工具本身只是一小部分，围绕工具构建的保障机制才是核心。

### 常见的 Agent 设计反模式

根据我的理解，以下是几个常见的错误做法：

- **上下文设计不良**：系统提示词过于笼统，或者动态信息注入位置不对
- **工具定义模糊**：参数描述不清，导致模型频繁选错工具
- **缺乏反馈循环**：工具执行失败后，Agent 看不到错误信息，无法自我纠正
- **过早引入自主模式**：应该用工作流的场景，强行用自主 Agent，导致不可控

## Part 6：工程范式的演进

五个阶段层层包含：

- **软件工程**：传统系统设计、架构、测试和部署
- **提示工程**：优化输入给模型的自然语言指令
- **上下文工程**：系统性管理模型能看到的所有信息
- **Harness 工程**：模型之外的全部基础设施
- **Loop 工程**：跨轮次的持续自主运转

**当各家模型的能力越来越接近、不再是决定性的差异因素时，竞争优势就转移到了模型之外的工程实践。**

LangChain 的实践：仅通过优化 Harness（不换模型），在 Terminal Bench 2.0 上从 52.8% 提升到 66.5%，从排行榜 30 名开外跃升至前 5。

## Part 7：Harness 五个功能的核心原则

- **上下文**：信息充分性——让 Agent 在每个决策点都基于足够的信息判断
- **工具**：接口清晰——工具命名直观、参数有例子、边界有说明
- **约束**：故障安全默认值——所有能力默认关闭，必须显式开放
- **验证**：输入隔离——安全检查只看结构化数据，而不是模型自由生成的文本
- **纠正**：在确认无法恢复之前，不暴露中间态

## Part 8：构建有效 Agent 的三个原则

根据 Anthropic 的经验：

### 1. 保持简单

从最简单的方案开始，只在确实必要时才增加复杂度。直接的 API 调用优于复杂的框架，清晰的代码优于聪明的抽象。因为每多一层抽象都会成为以后调试时新的盲区。

### 2. 保持透明

明确显示 Agent 的规划步骤、执行日志和决策轨迹。黑箱里的错误一旦发生，外部观察者既无法定位也无法纠正。

### 3. 设计好工具接口（ACI）

ACI 强调从 Agent 视角设计接口（让 Agent 容易理解和使用），而非传统 API 从程序员视角设计。工具的命名和参数要直观，容易误用的地方要主动防呆。

这种"用设计消除错误"的思路在制造业里叫**防呆**（Poka-yoke），源自丰田生产体系。

## Part 9：编排模式——工作流与自主

### 工作流模式

通过预定义的代码路径来编排 LLM 和工具。执行路径是确定性的，由开发者预先设计好。

**优势**：严格的流程控制、安全性高（攻击面限制在单个节点内）

**局限**：缺乏变通性，无法灵活应对预设流程未覆盖的情况

### 自主 Agent

执行路径不是预先定义的，而是 Agent 根据环境反馈实时决定的。

**优势**：能处理开放式问题，灵活应对各种情况

**局限**：更高的成本和潜在的复合错误风险

### 选择原则

实践中，工作流和自主 Agent 并非非此即彼——很多系统会混合使用两种模式。

**原则**：先优化提示词，再考虑工作流，最后才引入自主 Agent——这是降低意外风险最实用的顺序。

## Part 10：护栏与安全性

单个护栏不太可能提供足够的保护，但将多个专门的护栏组合使用，就能构建出更有韧性的 Agent 系统。

### 护栏类型

**输入侧**：
- 相关性分类器：标记偏离主题的查询
- 安全分类器：检测越狱和提示注入
- 内容审核：标记有害或不当的输入
- 基于规则的保护：黑名单、输入长度限制、正则过滤器

**执行侧**：
- 工具风险评级：根据操作是否可逆、权限等级、财务影响标注风险等级

**输出侧**：
- PII 过滤器：审查输出中的个人身份信息
- 输出验证：确保回复与品牌价值一致

### 人工干预

两种触发情况：
1. **超过失败阈值**：Agent 的重试次数或操作次数超过上限
2. **高风险操作**：涉及敏感、不可逆或高风险的操作

## Part 11：如何选择模型

### "御三家"

- **OpenAI（GPT/o 系列）**：各方面能力均衡，用户数量最多
- **Anthropic（Claude 系列）**：复杂推理、编程和工具调用表现突出
- **Google（Gemini 系列）**：超长上下文窗口和强大的多模态能力

### 国内模型

- **豆包系列**：国内延迟极低，适合实时交互
- **Kimi**：国内 Agent 能力较强的模型
- **Qwen 和 DeepSeek**：开源模型，在成本和可定制性方面有优势

### 选型原则

- **不要只看排行榜**，要在你自己的任务上做评估
- **绝大多数 Agent 需要支持思考（Reasoning）的模型**
- 关注**输出 token 的速度**和**多模态支持**

## 本章小结

1. **Agent = 大脑 + 眼睛 + 手脚**：LLM 是大脑，上下文是眼睛，工具是手脚。三者缺一不可。

2. **上下文是决定性因素**：消融实验表明，去掉任何一个组件都会导致系统显著退化。

3. **Harness 是竞争力所在**：模型能力正在商品化，真正的差异在于 Harness——约束、验证与纠正机制，确保 Agent "可靠地做事"。

4. **从工作流到自主 Agent**：先简单后复杂，每种编排模式都有适用场景。

5. **安全是架构问题**：从第一行代码就要考虑，而不是上线前打补丁。

---

## 开放问题

几个值得思考的问题，欢迎讨论：

1. **模型 vs Harness 的边界**：模型每内化一种能力，对应的 Harness 层就可以删掉。但这个"吃"永远不会完结——你觉得哪些 Harness 最先被吃掉？哪些最不可能？

2. **上下文成本**：ReAct 循环中，每次 LLM 调用都看到完整历史轨迹，成本随长度二次方增长。有没有办法在不丢失关键信息的前提下打破这个二次方？

3. **工作流 vs 自主的选择**：如果你要设计一个航班订票客服系统，你会选工作流还是自主 Agent？还是混合？

4. **工具风险评级**：如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险（如 delete_file 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？
